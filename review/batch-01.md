# Show HN · 第 1 批品味校准

每个项目只需要回复：**值得推 / 不值得推 / 信息不足**，加一句原因。也可以补充“有原创性，但我不感兴趣”。

本页隐藏票数和榜单状态。每张卡附有助手的建议判断与理由，方便快速审阅；它不是你的标签，只是对照参考，不同意直接改判即可。以下是来源材料的摘要，作者的性能与效果主张尚未独立验证。第一轮用于校准品味，不是已确认未上榜的推送名单。

例如：`01 值得推：这个约束下的做法让我想到新的应用。02 不值得推：只是已有工具的组合。`

## 01 · Commit-quiz · 提交代码前，先考考提交者

**做什么：** 一个 Git pre-commit hook：在提交 AI 生成的改动前，要求开发者回答关于本次 diff 的问题。

**具体做法：** 调用已有 AI CLI，把 staged diff 变成四个陈述，其中两个正确、两个貌似合理但错误。答错会中止提交并展示真实改动摘要；模型或交互不可用时放行。

**材料边界：** 已读 README，未安装试用。尚不清楚题目能否测出理解程度，以及长期使用是否变成机械答题。

**来源：** [项目 / README](https://github.com/Cristopheer96/commit-quiz) · [HN 原帖与作者说明](https://news.ycombinator.com/item?id=50191433)

**助手建议：** 值得进一步看　**理由：** 它把检查对象转向提交者是否理解改动，而不仅是代码有没有问题；机制能直接针对 AI 编程中的责任与理解脱节。

**待验证：** 试做真实 diff 的题目，检查猜答案的难度、误判率及与已有代码理解测验工具的区别。

**你的判断：** 值得推　　**原因：**

## 02 · Lossy Git · 把代码提交进神经网络

**做什么：** 一个浏览器实验：commit 时训练小神经网络记住文件，checkout 时从权重重建，文件可能被记错。

**具体做法：** 用位置编码映射代码字节或图像像素；可以调网络大小和训练次数，对照原文件与重建结果，观察压缩与错误之间的关系。

**材料边界：** 已读演示页说明，未运行页面里的代码。它明确定位为实验，不能当可靠版本控制系统。

**来源：** [项目 / README](https://nicobrenner.github.io/lossy-git/demo.html) · [HN 原帖与作者说明](https://news.ycombinator.com/item?id=50179254)

**助手建议：** 值得进一步看　**理由：** 把不可接受的数据损坏变成可观察的学习材料；用户能通过熟悉的 commit/checkout 理解参数记忆的局限。

**待验证：** 亲自验证不同网络容量的错误，并比较它与已有神经压缩演示的交互差异。

**你的判断：** 不值得推 　　**原因：**

## 03 · Moodly · 只存在浏览器里的心情日记

**做什么：** 选择日期、五档心情和可选备注，生成月历与心情分布，支持导出 JSON/CSV。

**具体做法：** 记录保存在当前浏览器站点数据中，无账户、云备份或跨设备同步；页面明确提示清理浏览器数据会丢失记录。

**材料边界：** 已读实际表单和数据说明，未写入记录；没有查看源代码或比较其他心情记录工具。

**来源：** [项目 / README](https://mood-tracker.org/) · [HN 原帖与作者说明](https://news.ycombinator.com/item?id=50185268)

**助手建议：** 暂不推　**理由：** 工具的边界清楚，但本地保存、月历和导出这组功能尚未给出足够具体的新想法。

**待验证：** 如果用户特别重视极简本地工具，再评估它的操作细节；不能仅凭免费和隐私就认定原创。

**你的判断：** 值得推　　**原因：** 比较有意思的产品思路

## 04 · Non-call · 一场没有胜利条件的值班夜

**做什么：** 一个模拟工程师夜间 on-call 的小游戏：从深夜撑到早上交班，同时面对告警与生活打断。

**具体做法：** 起始界面写明告警会重叠、生活事件有倒计时、不作决定也有后果；到 07:00 就交班，不要求把所有事情解决。

**材料边界：** 已用浏览器查看起始界面与规则，尚未完成一局；暂不能评价游戏节奏和重复可玩性。

**来源：** [项目 / README](https://serum.sh/non-call/) · [HN 原帖与作者说明](https://news.ycombinator.com/item?id=50178183)

**助手建议：** 值得进一步看　**理由：** 用没有终极胜利的游戏规则表达值班工作的结构性冲突，值得检验它是否把工程经验转成了可感受的 insight。

**待验证：** 玩一局，观察工作与生活的选择是否影响局面，而非仅是随机弹窗。

**你的判断：** 值得推 　　**原因：**

## 05 · Melra · 写操作结果不明时，先停下来核对

**做什么：** 一个供 agent 调用的本地执行层，统一检查工具权限、验证执行证据，并记录操作回执。

**具体做法：** 对经过它的任务写操作，在派发前记录状态并限制最多派发一次；超时或崩溃后若无法确认结果，就进入待核对状态，不盲目重放。文档明确外部效果的 exactly-once 仍依赖服务方。

**材料边界：** 已读 README，未做故障注入。只约束经由该运行时的调用；存储状态和核对逻辑的可靠性尚未验证。

**来源：** [项目 / README](https://github.com/XAGI-Lab/melra) · [HN 原帖与作者说明](https://news.ycombinator.com/item?id=50173690)

**助手建议：** 值得进一步看　**理由：** 它把“请求失败”与“副作用可能已发生”分开处理，这个具体边界比泛泛的 agent 安全宣传更有解释力。

**待验证：** 构造服务已写入但响应丢失的场景，验证是否重复派发，以及恢复证据不足时如何处理。

**你的判断：** 不值得推 　　**原因：**

## 06 · ANE Fieldfare · 用 ANE、GPU 和文件缓存协作推理

**做什么：** 在 Apple Silicon 上运行稀疏专家模型的实验实现，试图降低预填充延迟并提高生成速度。

**具体做法：** README 描述 GPU 解包量化专家、ANE 进行部分预填充计算，生成时在 GPU 上做推测解码，并通过 mmap 让操作系统文件缓存承载专家权重。

**材料边界：** 作者给出分工作负载的测量，未独立复现。标题的峰值速度不是普遍速度；较小的进程 RSS 不代表操作系统缓存不占内存。使用私有 Apple 接口。

**来源：** [项目 / README](https://github.com/zw5/ane-fieldfare) · [HN 原帖与作者说明](https://news.ycombinator.com/item?id=50174998)

**助手建议：** 值得进一步看　**理由：** 有具体的硬件分工和内存取舍可以研究，价值来自机制与测量，不是标题里的峰值数字。

**待验证：** 在相同模型、采样参数和提示词上对照上游 Turbo Fieldfare，测量总内存、缓存、功耗和速度。

**你的判断：** 不值得推 　　**原因：**

## 07 · Riff · 用缩放浏览日历

**做什么：** 一个 iPhone 日历，通过连续缩放从半年移动到单日，缩放过程中的各层都能查看和操作事件。

**具体做法：** 用户在时间网格中长按建事件、拖动长度，或把事件提起来，移动到其他日期再放下；直接使用手机已有日历。

**材料边界：** 已读作者说明和产品页，未在 iPhone 实测。作者主动说明后来发现这个想法并非全新，认为差异在执行体验。

**来源：** [项目 / README](https://riffcalendar.com) · [HN 原帖与作者说明](https://news.ycombinator.com/item?id=50183591)

**助手建议：** 信息不足　**理由：** 它是“概念已有，但执行可能带来新体验”的边界案例；只读文字无法判断连续缩放是否足以构成推荐理由。

**待验证：** 看完整操作演示，比较缩放时的事件可读性和编辑行为，并询问用户是否把优秀执行纳入目标。

**你的判断：** 值得推 　　**原因：** 有意思的产品idea

## 09 · HarnessHive · 多人一起设计实体线束

**做什么：** 面向线束工程师的浏览器设计工具，把电路逻辑、实体布线、物料清单和制造图放在同一工程中。

**具体做法：** 四个视图共享一个模型，修改线束后材料和裁线长度跟随更新，并导出 1:1 装配板图；元件实例固定其库版本，支持实时协作。

**材料边界：** 已读作者介绍与功能说明，没有进入需注册的产品；尚未对照其他线束 CAD 的相应功能。

**来源：** [项目 / README](https://harnesshive.com) · [HN 原帖与作者说明](https://news.ycombinator.com/item?id=50190012)

**助手建议：** 信息不足　**理由：** 多视图一致性与元件版本固定是具体设计，但这些机制在该领域是否稀缺，仍需要行业参照。

**待验证：** 选一个实际线束改动，观察多视图如何同步，并与现有线束工具比较。
