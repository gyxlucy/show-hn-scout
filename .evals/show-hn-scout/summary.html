Show HN Scout · select_project 评测

目标:判断一个 agent 能不能像 Lucy 一样,从 Show HN 里挑出值得打断她的项目(push / pass / unsure)。 状态截至 2026-10-24。

一句话结论
  • 原来的判断标准(rubric v0)和 Lucy 的口味不一致。用 v0 写的 agent 在保留集上只和 Lucy 一致 23%,低于"全部推"的 57%。它几乎不推 Lucy 想看的东西(push 召回约 12%)。
  • 换成她自己的口味(rubric v1)后,agree 升到 70%,这是整个项目里最大、最可信的提升(+47 点,配对 95% CI +20 到 +70)。
  • v1 过度推送:Lucy 标 pass 的案例它大多也推。再加一条她自己说过的 pass 理由(太底层、太技术、她用不到),得到 v3:保留集 agree 76%,pass 识别 46% → 64%。
  • v3 相对 v1 的提升(+5.6 点)在噪声范围内(CI −5.6 到 +17.8),没达到我们预设的 +15 点门槛。当前只能把 v3 当候选,不能宣称它更好。
  • 相对"全部推"这个朴素答案,v3 只是勉强领先(+19 点,CI 0 到 +39)。要放心上线,还需要一批全新的盲测案例。

1. 这个项目在评什么

Show HN Scout 是一个 Python CLI,抓取 Show HN 帖子并冻结成证据包(标题、项目链接、页面正文、HN 评论、浏览器快照)。select_project(evidence, preferences) 是其中最关键的一步:读一份证据,回答 push(值得打断读者)、pass 或 unsure,并给出中文理由。

本评测用的"标准答案"只有一个来源:Lucy 的人工标签。评测本身是真实的 Cavia 任务(POST /v1/tasks,由 system-prompt.md + request.json 定义),不是直接调用模型。

2. 过程时间线

10-22 · 开发集建立抓取 30 个案例(15 个随机 + 15 个刻意挑选的边界案例),Lucy 逐个标注 push/pass(15/15),部分写了理由。这 30 个案例同时用来校准 rubric,所以只能当开发集。
10-23 · 评测搭建与试点建 baseline agent(只依据 rubric v0)、程序打分 + judge 打分、selftest。冒烟 → 试点(claude-haiku-5-5,30 × 1):agree 27%。随后完成两次签字确认:案例集、打分方式。
10-23 · rubric v1 草案把 Lucy 的理由整理成 v1:"产品点子有意思"为主标准,新颖不是必须;受众太窄、页面杂乱或读不到判 pass;unsure 只留给无法消解的矛盾。她删除了我推断的 4 条类别规则(开发基础设施、教程、纯技术实验、视觉硬件折腾,都只是巧合)。
10-23 · 保留集新抽 30 个案例(纯随机,HN id 大于开发集),盲标(卡片不显示助手的判断),17 push / 13 pass。保留集标签和结果不进公开仓库。
10-23 · 三个模型baseline 与 v1 各跑 3 次:claude-haiku-5-5、bright-rain、washed-bacon。后两者在 JSON 前输出 <think> 块,被严格解析器判无效,所以只做描述性对比。
10-24 · haiku 爬升(hillclimb)第 1 轮:v1 prompt。第 2 轮:v3,即 v1 加一条 pass 规则(来自 Lucy 对 02、12、25、29 的理由)。每轮需要她批准,第 2 轮后她选择收尾。

3. 数据集

集合案例分布用途与限制
开发集 dev(= train)3015 push / 15 pass,随机 15 + 刻意挑选 15。常数答案 50%用来写 rubric,不能证明改进。标注时看得到助手的判断(锚定偏差)。
保留集 held-out(= test)3017 push / 13 pass,纯随机。"全部推"得 57%盲标。但被用来在第 1、2 轮间做选择,所以有选择偏差;4 个案例页面正文为空。

所有成绩都是 30 个案例 × 3 次重复 = 90 行。实测同一案例 3 次的决定基本不变(26–28 个案例完全一致),所以重复次数带来的信息很少,案例数才是精度瓶颈。30 个案例的噪声范围约 ±14–16 个百分点。

4. 怎么打分

  • 决定(程序打分):agree = agent 的 push/pass 与 Lucy 一致;unsure 一律算不一致。辅助指标:push 精度(分母是实际推送数)、push 召回、pass 识别率、unsure 率、格式有效率。
  • 理由(judge 打分):claude-opus-5-5 只看理由,不看决定,评 grounded(事实能在证据里找到)、specific(点名这篇帖子的具体内容)、consistent(理由支持所给决定)。judge 不会是被测模型。
  • 严格解析器:回复必须是单个 JSON 对象。事后诊断提取(找最后一个 {"decision"...})另外报告,不混入主成绩。
  • 置信区间:按案例聚类的 bootstrap。配对差值也按案例聚类。区间重叠就不宣称改进。
  • 不用:票数、stars、排名、营收、UI 精致度、代码量。

7. 主要发现

  1. 原标准要求"具体机制 + 可迁移 insight",而 Lucy 推的理由是产品口味("有意思的小产品""有创意""垂类小产品"),她甚至说案例 26"不新颖也推"。这就是 baseline 几乎不推的原因。换成她的口味后,提升最大。
  2. pass 边界没学会。她写过理由的 pass 案例只有 2/15(14:"受众太 geek 小众",22:"页面太复杂,很 slop")。分析 agent 读开发集痕迹后发现:pass/push 标签有一部分在可见证据上区分不开(如 02、27、09 更像她的 push)。再提升需要她提供 pass 理由,而不是更聪明的提示词。
  3. 她新补的理由是同一条规则:02(太深入神经网络底层)、12(防火墙太 technical,用不到)、29(tree-sitter/wasm 太小众太细节)、25(太细节,场景用不上)。写成"低层或高度技术性组件,深度到读者自己不会用 → pass"后,pass 识别从 46% 到 64%,push 召回只降 4 点。
  4. 推断出来的类别规则被她否决了。"开发基础设施 / 教程 / 纯技术实验 / 视觉硬件折腾都 pass"被她确认为巧合,已删除。规则要标来源:[她说] 或 [推断]。
  5. haiku 的理由有 1/3 到 1/2 是英文(基线保留集 42/90),尽管指令要求中文。这一项当时被接受,没有改。
  6. 推理类模型(bright-rain、washed-bacon)的 <think> 输出让严格评测基本不可用。需要服务商关闭,或批准使用宽松解析器。

8. 能信到什么程度

可信

  • 标准答案只有 Lucy 的标签;保留集盲标,且 rubric v1 不是从它写出来的。
  • 每行都是真实 Cavia 任务,记录了实际服务的模型(claude-haiku-5-5)、token 用量和 0 次工具调用。
  • 头条数字从原始回复重算,与存储的打分一致。
  • judge 不是被测模型;分析 agent 只读过开发集痕迹,没见过保留集标签或痕迹。
  • v1 − baseline 的提升(+47 点,CI 不含 0)远大于噪声。

限制

  • 保留集在第 1、2 轮用来选择,数字有选择偏差,需要新的盲测集做最终数字。
  • 30 个案例的噪声约 ±14–16 点;v3 对 v1 的 +5.6 点分不开。
  • 开发集上 v3 的数字被污染。
  • v3 在某个 Lucy 标 push 的保留集案例上从 3/3 变成 0/3;为不让保留集影响调参,没有去看它。
  • 只有 haiku 做了爬升;跨模型对比是描述性的。
  • 保留集一次运行遇到 4 次临时证书错误(重跑续完);费用没有测量,只有 token。

10. 建议与待决事项

  1. 采用 v3/system-prompt.md 作为候选,但不把它说成"已证明更好"。理由:push 召回基本保持,pass 识别明显更好,没有额外成本。
  2. 请 Lucy 再标一批全新的盲测案例(建议 30 个),在 v1 和 v3 之间做最终裁决。这是把"候选"变成"结论"最缺的一步。
  3. v3 里"有创意的技术呈现仍然推"一句是我从案例 15 推断的,需要 Lucy 确认或删除。
  4. 05、08、09、27、28 还缺 pass 理由,补上能进一步澄清 pass 边界。新的判断标准版本需要新的保留集。
  5. 推理类模型的 <think> 问题:联系服务商关闭,或批准使用宽松解析器后重跑。
  6. 未尝试:给 push 加 few-shot 示例;更多 pass 理由;更大的案例集(案例数是精度瓶颈,比增加重复次数更有效)。
